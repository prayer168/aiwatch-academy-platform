# 熊掌智境 AI Watch V1.1 Codex 實際開發任務包

版本：V1.1｜依據：營運與技術計畫書 V1.0（2026-10-25）

## 目的與交付範圍

本任務包把 V1.0 的營運構想拆成可估時、可實作、可測試、可驗收的 GitHub Issues。第一個可上線版本包含：公開網站與內容頁、註冊登入、分級會員中心、Supabase 資料層與 RLS、台灣金流 Adapter 與沙盒流程、LINE 身分綁定、電子報同意與 ESP 介面、管理工具、監控與上線驗收。

五個流量入口（Facebook、YouTube、官網、LINE、電子報）共用官網會員身分。Facebook 與 YouTube 在本期是外部導流入口，不做登入授權或內容同步。收費不代表外部社團自動具備可靠的付費授權能力；付費資源一律回官網授權。

## 建議技術與決策邊界

- Next.js App Router、TypeScript；單一 web app 加 billing、messaging、db 模組，避免過早拆微服務。
- Supabase Auth、Postgres、Storage；RLS 預設拒絕，付費判斷由可信任伺服器端執行。
- 金流、電子報 ESP、LINE Messaging API 均以 Adapter 隔離供應商。第一個正式金流、ESP、部署網域與部署平台需在開始相依 Issue 前決定。
- 正式價格採 V1.0 假設值：FREE NT$0、STARTER NT$199/月、PRO NT$499/月。上線前由營運方確認價格、續訂、取消、退款、寬限期與稅務揭露。
- 優先用月方案；不把試用、年繳、折扣券、發票平台、個人化服務列入 MVP。
- 電子報行銷同意與服務通知分離；LINE 加好友與網站會員分離；只有會員明確綁定才連結帳號。

## Label 與 Issue 慣例

建立 Labels：`epic`、`phase:foundation`、`phase:mvp`、`phase:launch`、`area:web`、`area:db`、`area:auth`、`area:billing`、`area:line`、`area:newsletter`、`area:admin`、`area:security`、`type:decision`、`type:docs`。每張 Issue 使用下方標題、描述、驗收條件與依賴。Epic 是追蹤容器，實作項目使用 Task/Story Issue 並連回 Epic。

## Epic 清單與建議順序

| 順序 | Epic | 目標 | 驗收出口 |
|---|---|---|---|
| E0 | 決策、Repo 與交付基礎 | 鎖定供應商、環境、CI 與技術決策 | 新開發者可啟動；Secrets 不進版控；CI 阻擋失敗合併 |
| E1 | 官網資訊架構與公開內容 | 五入口導流至可索引的品牌官網 | 手機可用、SEO 基礎完整、UTM 保留 |
| E2 | Auth、會員中心與溝通偏好 | 單一帳號、明示同意、資料可自助管理 | 註冊驗證、復原、偏好與資料權利流程可用 |
| E3 | Supabase Schema、RLS 與資源授權 | 建立資料來源與伺服器授權 | FREE/STARTER/PRO 越權測試通過 |
| E4 | 訂單、金流與訂閱生命週期 | 沙盒付款、Webhook、取消、退款與對帳 | 重送事件不重複入帳/授權；回跳不影響開權 |
| E5 | LINE OA 身分綁定 | 經同意將 LINE 身分連至會員 | 綁定/解除安全；不以暱稱比對 |
| E6 | 電子報與 ESP 串接 | 雙重確認、分群、退訂與寄送事件 | 退訂有效；交易信與行銷信分離 |
| E7 | 管理、分析、可觀測性與上線 | 支援稽核、營運與恢復演練 | UAT、備份還原、告警、上線檢核完成 |

## GitHub Issues

### E0 決策、Repo 與交付基礎

#### [E0-01] 確認 MVP 產品與營運決策
Labels: `epic` `type:decision` `phase:foundation`

**描述**：在實作付款與訊息供應商前，由產品負責人核定價格、方案權益、續訂/取消/退款規則、寬限期、客服方式、未成年政策適用範圍，以及金流/ESP/網域/部署平台。V1.0 的 199/499 元僅是規劃假設。

**驗收條件**
- [ ] 決策紀錄列出 FREE、STARTER、PRO 權益矩陣與每項資源的 access tier。
- [ ] 明訂續訂週期、失敗付款寬限期、取消生效時間、退款與權限撤銷規則。
- [ ] 指定金流商及其定期扣款、Webhook 簽章、退款、測試環境支援狀況。
- [ ] 指定 ESP、LINE OA API 用途、主網域、部署區域與資料處理/保留需求。
- [ ] 未決事項明列負責人與期限；任何收費功能不可用未核定規則上線。

#### [E0-02] 建立應用程式骨架與 CI
Labels: `phase:foundation` `area:web` `area:security`
依賴：E0-01（供應商細節可晚些完成）

**描述**：建立 Next.js/TypeScript 專案骨架、格式檢查、型別檢查、建置與 GitHub Actions。目標資料夾依 V1.0 建議，保持初期單體式模組化。

**驗收條件**
- [ ] 本機依 README 指令可安裝依賴並啟動開發伺服器。
- [ ] CI 執行 lint、typecheck、build；失敗會阻擋合併。
- [ ] `.env.example` 有變數名稱與用途，沒有真實密鑰。
- [ ] 開發/預覽/正式環境設定分開，服務端密鑰不會輸出到瀏覽器 bundle。
- [ ] 新增 ADR 記錄框架、目錄與部署決策。

**驗收條件**

- [ ] 不把尚未確認的網域、品牌權利或合作關係寫成既定事實。
- [ ] 無障礙基本操作：鍵盤焦點可見、表單有標籤、圖片有適切替代文字。

**驗收條件**

- [ ] 文章模板提供前提、步驟、錯誤排除、驗收結果、限制/來源與 CTA 欄位。
- [ ] 未登入使用者無法透過 API 取得付費正文或附件。
- [ ] 課程與文章有可分享的穩定 URL；不存在內容回 404。

#### [E1-03] 加入 SEO、分享中繼資料與 UTM 歸因
Labels: `phase:mvp` `area:web`

**描述**：依 V1.0 完成 SSR/預渲染、title/description、canonical、sitemap、robots、OG、Breadcrumb 與 first_touch/last_touch 歸因。

**驗收條件**
- [ ] 公開頁有唯一 title、description、canonical 與社群分享資訊。
- [ ] sitemap 僅列出可索引的已發布公開頁；robots 不誤封公開內容。
- [ ] `source`、`medium`、`campaign` 經註冊前導覽與登入流程保留並寫入歸因資料。
- [ ] 不記錄不必要的個人識別資料；追蹤方案與同意機制符合已核定隱私政策。
- [ ] 結構化資料只輸出該頁面真實存在且符合 schema 的欄位。

### E2 Auth、會員中心與溝通偏好

#### [E2-01] 建立 Email 驗證註冊、登入與帳號復原
Labels: `phase:mvp` `area:auth` `area:web`
依賴：E3-01

**描述**：使用 Supabase Auth 提供 Email 註冊驗證、登入、登出、忘記密碼與重設。註冊時接受服務條款，電子報行銷同意必須獨立且預設未勾選。

**驗收條件**
- [ ] 未驗證 Email 的帳號無法存取會員資源。
- [ ] 條款版本、接受時間與必要同意紀錄可追溯。
- [ ] 行銷 opt-in 不預設勾選；不勾選仍可建立免費帳號。
- [ ] 忘記密碼流程回應不洩漏指定 Email 是否已註冊。
- [ ] 重設連結過期/重用時安全失敗並提供可理解訊息。

#### [E2-02] 建立會員中心與自助資料管理
Labels: `phase:mvp` `area:auth` `area:web`
依賴：E2-01、E3-02

**描述**：會員可檢視目前方案、權益、訂單/訂閱摘要、內容入口、電子報與 LINE 偏好，並可提出資料匯出/刪除申請。

**驗收條件**
- [ ] 顯示的方案與期限由後端資料計算，不能由瀏覽器欄位自訂。
- [ ] 取消入口顯示生效日期及後續權限影響。
- [ ] 使用者可更新顯示名稱、行銷偏好與通知偏好。
- [ ] 資料匯出/刪除流程有請求狀態與稽核紀錄；法定保留資料依政策處理。
- [ ] 會員無法讀取其他會員個人資料或訂單。

### E3 Supabase Schema、RLS 與資源授權

#### [E3-01] 建立核心資料表與 Migration
Labels: `phase:foundation` `area:db`

**描述**：以版本化 migration 建立 profiles、member_plans、subscriptions、orders、payment_events、entitlements、contents、assets、newsletter_consents、line_bindings、attributions、audit_logs。補足主鍵、外鍵、唯一鍵、索引、時間欄位與狀態限制。

**驗收條件**
- [ ] migration 可從空資料庫重建，並有最小測試資料 seed（不含真實會員）。
- [ ] `profiles.id` 參照 Auth UID；付款金額採整數 TWD 並保存下單時價格快照。
- [ ] payment event 對 provider + event_id 設唯一約束；line_user_id 具唯一約束。
- [ ] 會員訂閱狀態與訂單狀態使用允許值約束或明確 enum。
- [ ] 外鍵刪除策略保護交易與稽核資料，不因刪除 profile 意外遺失法定記錄。
- [ ] README 說明本地、預覽、正式環境 migration 流程。

#### [E3-02] 設定 Supabase RLS 與角色邊界
Labels: `phase:foundation` `area:db` `area:security`
依賴：E3-01

**描述**：對所有含會員資料的表啟用 RLS，預設拒絕。會員只可讀改自己的允許欄位；管理員透過受控後端角色執行管理操作。

**驗收條件**
- [ ] 每張表都有 RLS policy，沒有政策的情況預設不可讀寫。
- [ ] anon、FREE、STARTER、PRO、admin 角色權限矩陣有文件與自動化 DB/API 測試。
- [ ] service role key 僅存在伺服器 Secret，絕不交付客戶端。
- [ ] 用戶不能自行更新 plan、subscription、entitlement、payment 狀態或 audit log。
- [ ] 跨會員讀取/修改測試全部拒絕。

#### [E3-03] 實作伺服器授權與受限資源下載
Labels: `phase:mvp` `area:db` `area:web` `area:security`
依賴：E3-02

**描述**：建立統一 access policy，伺服器端判斷 resource scope、tier、有效期限與狀態；私有 Storage 物件僅透過授權後短效 signed URL 下載。

**驗收條件**
- [ ] FREE 讀 STARTER/PRO、STARTER 讀 PRO 均回 403 或明確升級頁，API 與 UI 一致。
- [ ] 直接猜測 Storage key 或重用過期 URL 無法取得檔案。
- [ ] 到期、取消生效、退款撤權後，新的內容請求與下載立即依規則拒絕。
- [ ] 授權檢查記錄資源與結果但不記錄簽署 URL 或敏感內容。
- [ ] 有授權規則的單元/API 測試與測試帳號矩陣。

### E4 訂單、金流與訂閱生命週期

#### [E4-01] 建立 Billing Domain 與供應商 Adapter 合約
Labels: `phase:mvp` `area:billing`
依賴：E0-01、E3-01

**描述**：定義 Checkout、付款查詢、取消續訂、退款、Webhook 驗簽與正規化事件介面；初期只接一個由 E0 決定的台灣金流商。

**驗收條件**
- [ ] Adapter 介面及供應商差異寫入 ADR，業務邏輯不直接依賴供應商 payload。
- [ ] 金額、幣別、會員、訂單、方案均在伺服器端核對，不信任瀏覽器傳入金額。
- [ ] 沙盒憑證使用 Secrets；不存在時本機明確顯示未設定，不會打正式金流。
- [ ] 供應商不支援的功能回傳可辨識錯誤，不假裝完成。

#### [E4-02] 建立結帳、訂單與付款回跳頁
Labels: `phase:mvp` `area:billing` `area:web`
依賴：E4-01、E2-01

**描述**：會員選方案後由伺服器建立待付款訂單並導向供應商 Checkout。前端 success/cancel 回跳只顯示狀態，不直接開通權限。

**驗收條件**
- [ ] 只允許購買已啟用方案，金額與價格快照由伺服器取得。
- [ ] 重複點擊或重送請求不建立多筆有效重複訂單（具 idempotency）。
- [ ] 回跳成功但 webhook 尚未驗證時顯示「處理中」，不顯示付費內容。
- [ ] 取消/失敗/使用者關閉頁面均可回會員中心查看待處理狀態。
- [ ] 訂單頁不顯示完整付款卡資料。

#### [E4-03] 實作安全 Webhook、冪等與事件稽核
Labels: `phase:mvp` `area:billing` `area:security`
依賴：E4-01、E3-01

**描述**：驗簽、時間戳/防重放（若供應商支援）、allowlist 欄位、payload hash、唯一事件鍵及處理狀態；保存必要稽核資訊並設重試/死信處理。

**驗收條件**
- [ ] 無效簽章、未知訂單、金額/幣別不符均拒絕且不開通。
- [ ] 同一事件至少送三次只改變一次訂單、訂閱與 entitlement。
- [ ] 事件先入庫再處理；處理失敗可安全重試，無法處理者可由管理者查明。
- [ ] 紀錄不保存不必要的個資或付款敏感資料；原始 payload 按核定保留政策保存或遮罩。
- [ ] 有付款成功、續訂、失敗、取消、退款、重複、亂序通知測試。

#### [E4-04] 實作訂閱狀態機、取消、退款與對帳
Labels: `phase:mvp` `area:billing` `area:db`
依賴：E4-03、E3-03

**描述**：實作 `paid_active`、`past_due`、`grace_period`、`canceled`、`expired`、`refunded` 狀態轉移、權限更新與每日對帳工作。寬限日數採 E0-01 核定值。

**驗收條件**
- [ ] 每種合法狀態轉移有規則；非法或重複轉移不會延長期限或重開權限。
- [ ] 續費失敗進入核定寬限期並通知補繳；寬限期滿撤銷付費權益。
- [ ] 自助取消顯示並保存生效時間；退款依核定政策撤權且留稽核軌跡。
- [ ] 每日對帳比對供應商與本地狀態，異常建立告警/待處理項目，不自動猜測修正。
- [ ] 付款成功但瀏覽器未回跳仍依驗證 webhook 正確開權。

### E5 LINE OA 身分綁定

#### [E5-01] 建立 LINE 綁定與解除流程
Labels: `phase:mvp` `area:line` `area:auth` `area:security`
依賴：E0-01、E2-01、E3-01

**描述**：會員登入官網後啟動 LINE 綁定，以官方授權/Callback 驗證取得的 LINE user ID 綁定會員。LINE OA 好友狀態與官網會員狀態分開保存。

**驗收條件**
- [ ] 使用 state/nonce 或等效防 CSRF 機制驗證 callback，失效/重放 callback 被拒絕。
- [ ] 同一 LINE user ID 不可綁至多個會員；已綁者需明確解除或客服流程。
- [ ] 綁定與解除皆要求登入確認並寫稽核紀錄；不使用暱稱比對。
- [ ] 用戶可查看/解除綁定；解除後不再同步行銷分眾。
- [ ] LINE API 失效時網站核心登入與會員權限仍可使用。

#### [E5-02] LINE 通知 Adapter 與事件分眾同步
Labels: `phase:launch` `area:line`
依賴：E5-01、E4-04、E2-02

**描述**：提供模板化通知與興趣標籤同步；LINE 標籤是呈現快取，不是授權資料來源。初期推播需限額與人工核准。

**驗收條件**
- [ ] 訊息事件由後端 queue/worker 發出，失敗可重試且不重複轟炸會員。
- [ ] 訂閱取消/退款後更新對應分眾；權限始終查 entitlement。
- [ ] 有月推播配額/成本記錄與發送預覽/核准流程。
- [ ] 交易通知與行銷推播類型分開保存，遵循會員偏好與核定規則。

### E6 電子報與 ESP 串接

#### [E6-01] 建立溝通同意、雙重確認與退訂資料流程
Labels: `phase:mvp` `area:newsletter` `area:db` `area:security`
依賴：E3-01、E2-01

**描述**：保存不同名單的 opt-in、確認、opt-out 時間、來源與政策版本；Email 行銷與 LINE 偏好分開。服務必要通知另列交易通道。

**驗收條件**
- [ ] 行銷同意預設 false，免費會員可不訂電子報。
- [ ] 雙重確認連結一次性且有期限；重送確認安全冪等。
- [ ] 退訂連結不要求登入、可立即生效並避免再次匯入名單。
- [ ] 退訂行銷信不阻斷合法必要的帳務/安全通知。
- [ ] 名單、同意時間、來源、同意文字版本可供稽核與匯出。

#### [E6-02] 建立 ESP Adapter 與名單同步 Webhook
Labels: `phase:mvp` `area:newsletter`
依賴：E0-01、E6-01

**描述**：串接 E0 選定 ESP，支援免費/入門/進階名單或標籤、寄送、退信、投訴、退訂 webhook。會員資料庫仍是同意狀態來源。

**驗收條件**
- [ ] 同步遵循 opt-in 狀態；退信/投訴按政策抑制後續行銷信。
- [ ] ESP webhook 驗簽且冪等；供應商故障不遺失待處理事件。
- [ ] ESP 中的付費分群由有效 entitlement 更新，不以手動標籤作授權依據。
- [ ] 日誌不輸出完整信件內容或不必要個資。
- [ ] SPF、DKIM、DMARC 與寄送網域設定有部署文件及驗證紀錄。

#### [E6-03] 建立分級電子報預覽與寄送工作流
Labels: `phase:launch` `area:newsletter` `area:admin`
依賴：E6-02、E2-02

**描述**：管理者建立 draft、預覽不同會員分群、核准、排程、寄送與查看送達/點擊/退信摘要。初期不自動產生或直接發信。

**驗收條件**
- [ ] 草稿/核准/排程/寄送狀態可追蹤，寄送前顯示收件數與名單條件。
- [ ] STARTER/PRO 專屬連結需官網登入與伺服器授權，不寄送長效公開下載網址。
- [ ] 誤選名單可在寄送前取消；寄送後可查事件及錯誤摘要。
- [ ] 寄送工作流使用單一公告/審核步驟並有操作人稽核。

### E7 管理、分析、可觀測性與上線

#### [E7-01] 管理後台與 RBAC/操作稽核
Labels: `phase:launch` `area:admin` `area:security`
依賴：E3-02、E4-04

**描述**：提供最小管理功能：查會員方案與狀態、搜尋訂單/支付事件、檢查對帳異常、協助資料權利請求。採角色權限並記錄管理操作。

**驗收條件**
- [ ] 管理員操作需強化登入（2FA 若平台支援）與最小權限角色。
- [ ] 不能在後台讀取完整信用卡資料、密鑰或未遮罩的敏感 payload。
- [ ] 撤權、退款/權益調整等敏感操作要求理由並記錄 actor、時間、目標與前後狀態。
- [ ] 管理 API 伺服端授權；一般會員無法呼叫管理端點。
- [ ] 管理者異動/離職有撤權與密鑰輪替 SOP。

#### [E7-02] KPI 儀表板與隱私友善事件
Labels: `phase:launch` `area:admin`
依賴：E1-03、E4-04、E6-02

**描述**：呈現免費註冊轉換、Email 點擊/回站、付費轉換、MRR、月流失、內容使用、製作工時（人工匯入）與付款異常。指標定義沿用 V1.0。

**驗收條件**
- [ ] 每個 KPI 顯示公式、期間、時區、來源與資料更新時間。
- [ ] MRR 排除免費、試用、失敗付款及已退款訂閱；金額以核定規則標準化。
- [ ] 追蹤遵循隱私同意及保留政策，不收集未核准的跨站識別資料。
- [ ] 付款異常指標可 drill down 到去敏訂單/事件，不暴露付款敏感資料。

#### [E7-03] 告警、備份還原與上線檢核
Labels: `phase:launch` `area:security` `area:db`
依賴：E3-01、E4-04、E5-02、E6-02

**描述**：為註冊失敗、Webhook 驗證/處理錯誤、對帳差異、退信/投訴、授權拒絕異常與下載濫用設告警；建立備份與恢復演練及正式上線 checklist。

**驗收條件**
- [ ] 告警有嚴重度、負責人、去重、保留期與操作手冊。
- [ ] 加密備份與異地策略文件化；恢復演練驗證會員、訂閱、授權及資源參照。
- [ ] 上線前完成 RLS/越權檢查、付款 UAT、退款取消 UAT、退訂測試、404/sitemap 與手機檢查。
- [ ] 金流與 ESP 正式密鑰、DNS 設定、資料政策與客服聯絡方式均由負責人核定。
- [ ] 有回滾步驟、事故聯絡方式與上線後 24/72 小時檢查表。

## GitHub Project 建議欄位與 Sprint

欄位：Status（Backlog/Ready/In Progress/Review/Done）、Phase、Area、Estimate（1/2/3/5/8）、Owner、Blocked by、Release。不可估時的 Issue 先拆成有明確驗收的工作。

| 時間 | 交付 | Issues |
|---|---|---|
| Sprint 0 / W1 | 決策、Repo、環境與資料模型 | E0-01、E0-02、E3-01、E3-02 |
| Sprint 1 / W2–3 | 公開站、SEO、Auth、會員中心骨架 | E1-01、E1-03、E2-01、E2-02 |
| Sprint 2 / W4–5 | CMS/內容、權限、資源庫 | E1-02、E3-03 |
| Sprint 3 / W6–7 | 訂單、沙盒金流、訂閱狀態機 | E4-01 至 E4-04 |
| Sprint 4 / W8–9 | 同意管理、ESP、LINE 綁定 | E5-01、E6-01、E6-02 |
| Sprint 5 / W10–11 | 分級寄送、管理後台、指標 | E5-02、E6-03、E7-01、E7-02 |
| Sprint 6 / W12–13 | 告警、復原、UAT 與分階段上線 | E7-03 |

此時程是初步切分，需以一人/團隊實際投入量與供應商審核時間重排。付款正式上線須以金流合約、政策文件、稅務/兼職查核完成為條件。

## 跨 Issue Definition of Done

- 驗收條件有自動化測試或可重現的驗收步驟；不得以「看起來正常」結案。
- UI 有載入、空資料、錯誤與權限不足狀態；行動版可完成核心操作。
- API 驗證輸入、授權、速率限制與錯誤回應；敏感值不進日誌。
- Schema/政策變更有 migration、回滾或安全補償步驟。
- 會員資料操作有最小必要稽核；付款和訊息事件支援冪等重試。
- 文件更新包括本機設定、Secrets 名稱、部署設定與營運者處理方式。
- Done 前由非作者以 FREE、STARTER、PRO、管理者帳號驗收主要路徑。

## Issue 建立步驟

1. 在目標 repository 建立上述 labels 與 GitHub Project 欄位。
2. 先建立 E0-01 決策 Issue、E0-02 基礎 Issue 與各 Epic 容器。
3. 建立 Task Issues，保留標題、描述、驗收清單與依賴；在 GitHub 用 `blocked by`/`blocks` 建立關係。
4. 將 E0-01 未決選擇轉成有負責人與期限的決策子 Issue；供應商未決前，不把整合工作排入 Ready。
5. 第一個 Sprint 只承諾資料基礎與公開/免費會員路徑；完成 E2/E3 後才接支付沙盒，沙盒 UAT 通過後才評估正式收款。

目標 GitHub repository 尚未由 V1.0 指定；此文件可直接作為建立 Issues 的來源，確認 repository 後再依其模板/label 慣例匯入。
